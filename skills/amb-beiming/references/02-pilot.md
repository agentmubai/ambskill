# 02 S2 试点与校准

## 目标与产出

用 2–3 批真料把萃取规则调到"连续两批不用再改"，然后冻结。规则冻结前不许全量开工——全量后再改规则，前面的批全部要重抽。

产出：`work/docs/执行提示词.md`（规则的工程副本，含补丁记录，冻结后第 3 行是独立成行的「版本：冻结 vX.Y」）、`work/pilot/` 试点产物、`work/docs/加工样品.md`（使用者的第二个参与点）。完成 = 冻结版本行在（脚本只认这一行，说明文字里的"冻结"不算）+ 试点批全部 `settle --pilot --accept` 成 pilot-accepted 进 parts + 加工样品在；三者同时成立 status 才判 S2 完成。

## 动作

1. 选批：最长文件所在的批 + 一个不同形态的批；有 D（作品）组再加一批 D。`beiming.py pilot b003,b011`（预检报告没有三选一结论会被拒：第一个参与点不能跳；`--force` 越过并记 pipeline.md）。第一次运行会把 `references/extraction-rules.md` 复制成 `work/docs/执行提示词.md` v1.0——**派之前先填它第 6 节**：topics 白名单（10–20 类，名称取自语料与候选任务草案）与 skills 分池标签（候选任务的 ASCII 短名 + `cases`）。
2. 派子代理：每份 `work/prompts/extract-bNNN.md` 一个。等它们写完文件。
3. `beiming.py settle --pilot`（子代理都返回后再跑：原子文件与批次报告都还不存在的批算"未返回"，不改状态、退出码 1，不是失败）：机械核验三个文件（原子 JSONL、单元 JSONL、批次报告 `work/reports/pilot-bNNN.md`）都在、JSONL 合法、引文逐字命中、schema 必填与枚举（role / type / claim_scope / confidence / 单元 type / flags）、id 格式与唯一、原子↔单元互指都在本批、original ≤ 200 字。不过的看 batches.json 的 note，让子代理修（或 `extract --pilot … --regenerate` 重派）。已 done 的批要重核，点名 `settle b003 --pilot`。
4. `beiming.py read b003 --sample` 自己抽读；`beiming.py calibrate` 生成校准提示词，派一个子代理：它审判断质量、写加工样品、把补丁追加到执行提示词并升版本。
5. 你决定要不要再试一批：补丁涉及 schema / 白名单 / confidence / 去重 / 保真五项之一 → 必须再试一批（`pilot bNNN`；要重抽旧批先 `reset bNNN` 再 `pilot bNNN`）；连续两批只加条目或无补丁 → 把执行提示词第 3 行整行改成「版本：冻结 vX.Y」（版本号与补丁记录里最后一个一致）。
6. `beiming.py settle --pilot --accept` 把已 done 的试点批产物搬进 parts、标 pilot-accepted；未冻结时它拒绝（退出码 2，并说明是没有版本行、没有"冻结"字样、还是版本行后带了尾注）。把加工样品交使用者看，说明"这批料能萃出什么、萃不出什么"。

## 规则

- 试点批必须包含最长文件：漏读中段的问题只在长文件上暴露。
- 补丁只加条目，不改五项（schema、role/type/claim_scope 白名单、confidence 判据、去重规则、保真红线）。要改五项就不是补丁，是回到 v1.0 重新试点。
- 每条补丁指向试点里的具体 id 作证据；无证据不加。
- 冻结判据是"连续两批不改五项"加一条抽查：从最近一批抽约 30 条原子（不足 30 全查），重大误判（该丢没丢、归属错、confidence 明显错、原法被改写）不超过 3 条。达不到就停在小批继续校准，每次改规则重新计；不是"我觉得差不多了"。
- 规则升版后旧试点批不必全重抽：只是措辞澄清 → 不重抽；改了归属或保真口径 → 受影响形态的批 `reset` 后重抽（recover 只管 interrupted 批），判断写进 pipeline.md。
- 加工样品用第二人称对使用者写，10 条原子 + 2 个单元 + 覆盖印象 + 一段"能萃出什么"。使用者看的是"这像不像作者说的、有没有漏我最在意的"，不是 schema。
- 试点期间 confidence 的 high 占比高不是问题，不用规则压低。

## 依据

外层：扎根理论的编码饱和——规则连续两批不再变化才算稳定；用还在漂的规则放量，等于用错误规则烧掉全部语料。

内层（可观察）：
1. `work/docs/执行提示词.md` 有独立成行的「版本：冻结 vX.Y」（`extract` 与 `settle --accept` 只按这一行判；说明句里出现"冻结"不算）。
2. 冻结前最后两批的补丁都不触及五项（schema、白名单、confidence、去重、保真）。
3. 抽查约 30 条，重大误判 ≤ 3。
4. 每个试点批 `claimed_by = pilot-accepted`（产物已在 parts）；加工样品文件在。

为什么这样定：
- 五项不动：它们决定字段语义，一动之后合并库里同一字段两种含义。
- 样品给使用者：使用者一眼能看出"这不是作者说的、这是学员的话"，这类归属错脚本核不出来；等 S7 才发现时道层已经掺进去。

实测参照（上一版记录）：过早放量后前几批 confidence 偏松、打补丁后又有一段矫枉过正，两头都要重看；规则里写"high 不超过 60%"的配额被机械执行，后几批 high 掉到 0%，把嘉宾的第一手数据也降成了 medium。

## 模板

`work/docs/加工样品.md` 的结构由 `assets/prompts/calibrate.md` 规定，子代理生成。你交给使用者前只加一段：

```
## 你现在要看的
- 这 10 条像不像他/她本人说的？有没有哪条其实是别人说的？
- 这 2 个完整案例是不是你最想保留的那种？
- 你最在意的某个说法在不在里面？不在就告诉我在哪个文件。
```

执行提示词第 3 行（版本行）：`版本：v1.2（试点中，未冻结）` → 冻结时整行改为 `版本：冻结 v1.2`。只改这一行；别处写"冻结"脚本不认，这一行后面加括号说明脚本也不认。

## 常见失误

- 只试一批短的：全量后长文件大面积漏读。
- settle 没过就 calibrate：校准子代理在改写过的引文上做判断，补丁方向错。
- 把"high 占比 70%"当成规则问题去压：judgement 判据没错，作者本来就在讲自己做过的事。验收报告注明即可。
- 冻结后又"顺手补一条"：那一条对已抽批不生效，档案里同一字段两种口径。要补就升版本、标从哪批开始生效，并在验收报告写明。
