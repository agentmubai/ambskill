# 01 S1 盘点与预检

## 目标与产出

把一堆文件变成"能开工吗、能做出什么"的一页结论，交给使用者拍板。这是使用者的第一个参与点。

产出：`work/catalog.json`、`work/batches.json`（脚本）；`work/docs/预检报告.md`、`work/docs/候选任务草案.md`（你写）。完成 = 三者都在且预检报告含结论词（可开工 / 收缩范围 / 补料）。

## 动作

1. 向使用者拿两样东西：语料目录；一句"你想拿它具体做什么"的粗方向（比如"做直播的逐字稿、拉停留、卖货话术"）。**不要问他要清单**——实测使用者给不出结构化的"平时要做的事"清单，四次工程里四个执行者全部卡在这一步，而同一个人被问"你想拿它做什么"时一句话就答上来了。清单由你在第 5 步从语料里提候选、他做减法。两样都记进预检报告。语料不拷进工程。
2. `python3 <skill>/scripts/beiming.py survey --corpus <语料目录> --project <项目>-workspace`。脚本建工程目录、按子目录分组、给每个文件稳定编号（并记文件名标题 `title`：短视频、帖子的标题常常只在文件名里；`title` 已剥掉开头的日期 / 时间前缀与末尾短哈希，`file` 保留原名）、猜形态、切批、打印规模表与批次表。
3. 看规模表里的形态猜得对不对（A 访谈 / B 单讲师课 / C 多讲师短分享 / D 作者作品）。错的用 `--form g03=A` 重跑，只改形态不动批次。
4. 抽读 5–8 篇（各形态都覆盖）各读前 2000 字：确认是文本而非乱码、说话人能分清、是作者的话而非二手笔记；更重要的是看方法密度——作者在讲可复用的判断和动作，还是在讲观点和感想；抽到后面几篇不再出现新的方法类目说明料够了，还在冒新类目说明还没摸到边。catalog.nontext 里列的非文本文件告诉使用者转文本后 `--update`。
5. 列排除清单写进预检报告：转不了的、明显无关的、重复的，每条写理由；**按讲者名筛掉的必须单列并请使用者确认**。
6. 写预检报告与候选任务草案（模板见下），交使用者看结论。使用者说"可开工"再进 S2；`pilot` 会查预检报告有没有三选一结论，没有就拒绝（`--force` 越过并记 pipeline）。

## 规则

- 单批 ≤ 10 万字符（默认 `--max-chars 100000`），单文件超过则独立成批并标 oversized：子代理读超长批会漏中段，独立成批让它能分段回看。上限按子代理的上下文定：上下文小的调低（256K 级建议 `--max-chars 80000`）；上下文更大的也不建议调高，漏中段的风险来自长度本身，子代理不会报"读不完"，它会漏。`survey` 对超过 10 万的批打印提醒。
- 形态决定 S2 的试点选择与 S3 的读法：A 要分清访谈者与被访者；B 抽讲师、学员默认不抽；C 每篇讲者不同，speaker 必填；D 是作品，一文件一个 work 单元（text 由脚本从正文生成，子代理不抄）、role=作品；标题在文件名里的按 extraction-rules 第 2 节红线 17 抽。
- 预检结论只有三种：可开工 / 收缩范围（只做某几组）/ 补料（缺什么、补多少）。不写"建议考虑"。
- 候选任务草案按语料目录与文件名粗列，明确标"待 S4 按数据重排"；它是给使用者对照自己清单用的，不是承诺。
- 语料量的参考线：一个任务技能背后要有几十到上百条原子（上一版参考值约 80 条，不是硬线）。总字符不到约 10 万时预检报告要写明"可能只够 1–2 个任务"；SKILL.md 开工前第 5 条的"不到 8 万字不用本技能"是同一条参考线（不足两个任务，手写更便宜）。

## 依据

外层：扎根理论的理论饱和——抽读到新文件不再冒出新的方法类目，材料才算够；料够不够是先于一切加工的判断，所以预检独立成段并要使用者看结论。

内层（可观察）：
1. 预检报告结论是"可开工 / 收缩范围 / 补料"三者之一，并附排除清单。
2. catalog 里每个文件有三位号，`survey --update` 后旧号不变。
3. 每批 ≤ `--max-chars`；超长文件独立成批并标 oversized。

为什么这样定：
- 批上限：单批上下文 = 输入 + 三份输出 + 余量；越长的批子代理越容易漏掉中段，这是长度本身的风险，不是某个模型的毛病。
- 稳定文件号：id 里带文件号，重排会让已交付技能里的全部 id 失效。
- 三种结论：模糊结论让使用者以为已经开工，等到 S4 才发现语料不够。

实测参照（上一版记录）：每任务原子数的参考值约 80 条（不是硬线）。

## 模板

`work/docs/预检报告.md`（对使用者写，用"你"）：

```
# 预检报告

## 结论：可开工 | 收缩范围（只做 gXX、gYY）| 补料（缺 …）

## 你的语料
| 组 | 名称 | 形态 | 文件 | 字符 | 我抽读后的判断 |
（从 survey 的规模表抄，加最后一列）
非文本文件：N 个（列前 5 个），转成文本后我再加进来。

## 你是谁、给谁做（一段：你的行业、受众、主要发布渠道——S7 出题只从这里取背景）

## 你平时要做的事（你说的，我记下来的）
1. …
2. …

## 这批料大概能支撑什么
- 能：…（对应你清单的第几项）
- 勉强：…（原子可能不够，做出来会薄）
- 不能：…（语料没讲）

## 排除清单
| 文件 / 组 | 理由 |
（按讲者名筛掉的单列，请你确认）

## 你现在要决定的
- 按上面的结论开工吗？
- 收缩 / 补料的话，选哪个？
```

`work/docs/候选任务草案.md`：

```
# 候选任务草案（按目录粗列，待 S4 按数据重排）
| 候选任务 | 来自哪几组 | 对应你清单第几项 | 把握 |
```

## 常见失误

- 把语料拷进工程再盘点：路径变了，S9 增量时对不上原件。catalog 记原路径即可。
- 形态全猜 B 不核对：访谈组里被访者的话全标成讲师，S5 的道会掺进访谈者的观点。
- 预检报告写成流水线说明：使用者只要结论与要决定的事，术语一个不要。
- 没记使用者的粗方向：S4 拆合时没有"使用者要什么"这一边，任务全按语料切，做出来没人用。
- 反过来也错：**开工前就逼使用者交一份完整清单**。他给不出来，只会逼出一份他临时编的、和语料对不上的清单。正确顺序是：先要一句粗方向 → 你从语料提候选（`候选任务草案.md`，每条标"来自哪几组"与把握高/中/低）→ 他在候选上划掉和增补。
