# 09 S9 增量更新与改造

## 目标与产出

新语料来了（或使用者用后反馈），只改受影响的部分，不重做全套；冲突交使用者决定；回归不掉才算更新成功。也覆盖"把别人的现成 skill 改造成这套形态"。

产出：新批次的 parts 与 kb 更新（S1–S4 的脚本复用）、`work/docs/更新对照-<任务>.md`、`work/docs/冲突表-<任务>.md`（每任务一份，追加；多任务并行不共写一张表）、改动后的知识包与同步过去的草稿技能 references、回归题集报告、重新 deliver 的成品。完成 = check-layers 与 lint 通过、常备题集回归无任务掉到 WEAK、deliver 记录更新。

这一段是三处使用者参与点之外唯一会再找使用者的地方，只在冲突表里"作者自己没说明取舍"的行；不是新参与点。

## 动作

新料：

1. 新文件放进语料目录（新子目录成新组，或加进已有组）。`beiming.py survey --corpus <目录> --update`：只追加文件号与批次；已分批的文件按"组 + 文件名"识别，新组里与旧组同名的文件是新文件，会正常切进新批。
2. `extract` → 派子代理 → `settle` → `merge` → `audit`。规则用当前冻结版；新料形态与旧料差异大到规则不适用，回 S2 对新组单独试点并升版本。
3. `repool`：任务池重建；新原子进哪个池按 tasks.json 的 match，新标签归不进去就补 match。
4. `beiming.py update all --groups g07,g08` → 每任务一个子代理做覆盖对照、写本任务的冲突表、局部改动**知识包**（`work/kb/packs/<任务>/`）与草稿 SKILL.md 受影响的 Phase；它不直接改草稿的 references。
5. `check-layers all` → `compose all --sync-refs`（把改过的知识包三件重新复制进草稿 references，知识包与技能不会两套）→ `lint`（references 变了旧记录会显示 stale，必须重跑）→ `evaluate`（常备题集回归，只重答 new）→ `evaluate tally` → `evaluate report`。
6. 掉到 WEAK 的任务：回滚该任务的改动（用 git 或改前副本），把冲突表里对应行标"回滚，待使用者决定"。
7. 冲突表里"交使用者决定"的行给使用者看；决定后再改。
8. `deliver` 重新装配，版本号在 README 里加一行"更新记录"。

使用者反馈（没有新料）：把反馈写成"哪个任务、哪题型、哪一层"，直接回 S5 或 S6 改，走第 5–8 步。

改造外部 skill：使用者有它对应的原始语料 → 语料走 S1–S3，把它的 SKILL.md 与 references 另作一个"作品组"（形态 D，role=作品）一并抽原子，再走 S4–S8；原 skill 的判断进道、步骤进法。没有原始语料 → 只能做结构改造（把"按需读取"改成按编号定位、把观点改成有分支的 Phase），不能补它没有的知识；如实告诉使用者上限在哪。不直接改写它的文本。

## 规则

- 覆盖对照三分：已覆盖（补依据 id）/ 新增（加模块或分支，编号接末尾不重排）/ 冲突（进冲突表）。
- 冲突处理只有四种：以新为准 / 以旧为准 / 并存为分支 / 交使用者决定。作者自己没说明变化的，默认交使用者。
- 局部改：只改受影响的 Phase 与不判清单，不重写 SKILL.md；每处改动要能说出"为哪条新原子而改"。
- 回归用常备题集且只重答 new；对照答卷复用。
- 旧原子 id、旧模块号不重排、不复用。
- 知识库体检（每次 merge 后）：悬空引用 0、别名链无环、每任务池非空。merge 与 repool 的退出码已覆盖。

## 依据

外层：版本控制的 diff-then-merge——先覆盖对照再改，冲突不自动合并，交人裁决。

内层（可观察）：
1. 每个受影响任务有 `更新对照-<task>.md`。
2. 冲突表每行有使用者的决定或"待决定"。
3. 回归题集里没有任务掉到 WEAK。

为什么这样定：
- 局部改 + 回归：重写一个技能会丢掉原来验收过的分支，回归是唯一能发现它的手段。
- 冲突交使用者：作者在不同时期的相反说法哪条有效，只有使用者知道；模型"以新为准"是猜。
- 编号不重排：接收方旧成品里点名的 M07 若换了内容，旧链接全部失真。

## 模板

`work/docs/冲突表-<任务>.md`（每任务一份，追加，不覆盖）：

```
| 日期 | 任务 | 模块 | 旧主张（原子 id） | 新主张（原子 id） | 作者是否说明了变化 | 处理 |
```

成品 README 更新记录一行：`- <日期>：新增 gXX 组 N 文件；任务 A 新增 M12–M13；冲突 2 处（1 处待使用者决定）；常备题集回归全 PASS。`

## 常见失误

- 新料直接重跑 survey 不加 `--update`：脚本拒绝；若删了 catalog 重来，文件号全变，旧 id 失效。
- 新料用新规则、旧料不动：同一档案两种口径；要么新组单独试点并在验收报告写明，要么整体升版重抽。
- 更新后不回归："只加了两条"也可能让技能的分支顺序变了。
- 把反馈直接改进成品目录：下次 deliver 覆盖；改草稿。
- 没做覆盖对照就重跑全量 S3：新料多半重复旧料，重抽是白花 S3 的钱；先 `update` 出对照再决定。
