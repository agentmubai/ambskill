# 04 S4 能力方案与任务池

## 目标与产出

按原子的真实分布与使用者的任务清单，决定工具箱有哪几个任务技能；使用者确认后把原子重新分到任务池。这是使用者的第三个（也是最后一个）参与点。

产出：`work/docs/S4数据表.md`（脚本）、`work/docs/能力方案.md`（子代理或你）、`work/tasks.json`（你，使用者确认后）、`work/kb/pools/<任务>/`、`work/docs/S4重建任务池报告.md`（脚本）。完成 = tasks.json 含 confirmed_at，repool 记录通过且无无处归原子。

## 动作

1. `beiming.py plan`：出数据表与拆合提示词。
2. 派一个子代理写能力方案（或你自己按提示词写；这一步判断多、读入少，自己写也行）。它写两个文件：给使用者看的 `work/docs/能力方案.md`（无字段名、无脚本名）和给你看的 `work/docs/tasks草案.json`（按下面模板节的 schema）。
3. 你先审：每个任务能不能说清 输入 / 判断 / 交付；薄任务（method+tool < 30 或 high < 20）有没有并掉；使用者清单里有而语料不支撑的有没有列出来。
4. 交使用者确认。他会改名字、合并、砍任务、加"我更常做的是……"。**没有这一步不许进 S5**。
5. 按确认结果把 `tasks草案.json` 改成 `work/tasks.json`（改名、合并、砍任务都在这里落地；schema 见模板），填 `confirmed_at`。
6. `beiming.py repool`。它先查三样再分池：tasks.json 有 confirmed_at、每个任务 input / judge / deliver 三格非空、能力方案里给使用者看的作者原话逐字且原子 id 对得上（`「……」（c01_003_012）` 写法；这是使用者亲眼看的引文，不逐字不分池）。无处归原子 → 补进某任务的 match 或加任务，重跑到 0。池薄的任务（< 80 条，参考值）回方案并入邻居。

## 规则

- 任务数不预设，由"使用者高频任务 × 数据支撑"决定。
- 每个任务必须能回答三问：使用者带什么来、作者的哪套判断决定走哪条路、使用者拿什么走。答不出"交付什么"的不是任务，是话题。
- skills 标签是 S3 的分池标签，不等于任务；S4 就是把标签重新装配成任务的过程。
- 命名用任务说话，不用内部分类术语：任务名与技能目录名写使用者要做的事（"选品判断""开头改写"），不写抽取时的标签名、六层名、"方法论 A 类"这类分类词；能力方案里给使用者看的名字与最终目录名对应，他改了名字就改 `name`。
- 副本引用：一条原子可以进多个任务池（tasks 顺序靠前的是主池，其余标 `_copy_of`），但单元只跟主池。
- 使用者确认的内容写进 tasks.json 的 `user_note`，S7 出题与验收报告都要回看它。

## 依据

外层：任务分析 / JTBD——能力的单位是"给什么、判断什么、交什么"，按使用者要完成的事拆，不按课程章节拆。

内层（可观察）：
1. `tasks.json` 含 `confirmed_at`，且每个任务的 input / judge / deliver 三格非空（repool 查）。
2. `repool` 无处归原子为 0，无空池。
3. 能力方案里列了被排除的候选及原因。

为什么这样定：
- 使用者必须确认：任务体系是使用者用的；执行方按语料切出的任务再合理，也可能是他从不做的事。
- 三问：没有交付物的"任务"在验收里没有可评的东西。
- 薄任务并入：原子太少的池撑不起道法术三层。

实测参照（上一版记录）：一次工程里执行方未经使用者确认就把候选任务定稿为 13 个并直接生成、验收、打包，使用者拿到成品时根本没见过能力清单，整套返工；每任务原子数的参考值约 80 条（不是硬线）。

## 模板

`work/tasks.json`：

```json
{
 "prefix": "xx",
 "toolbox": "工具箱名（可空，deliver 时给）",
 "confirmed_at": "2026-01-01T12:00:00（使用者确认后才填；空则 repool 拒绝）",
 "user_note": "使用者确认时说的话，原样记",
 "tasks": [
  {"id": "positioning", "name": "定位诊断", "domain": "定位",
   "input": "使用者带来的事实：…", "judge": "作者的哪套判断：…", "deliver": "使用者拿走：…",
   "match": {"skills": ["定位", "差异化"], "topics": ["人群"], "groups": ["g02"]},
   "user_job": 2}
 ]
}
```

- `id` ASCII 短名，将成为技能目录名 `<prefix>-<id>`；`domain` 是知识包标题用的中文名。
- `match` 三项任选，命中任一即归入；`groups` 用来把整组（如作品集）划给某任务。
- `user_job` 对应预检报告里使用者清单的第几项；可选任务写 0。
- `no_case`（可省，默认 false）：语料里确实没有该任务的完整案例时标 true。标了之后 S5 index 不因缺卡判未完成，S6 技能要如实写「本任务无现场案例」、不引 cases.md，lint 改查这一句。**只在案例库里真的一个都对不上时才标**——是"没有"，不是"懒得找"；纯方法型任务（作者只讲了怎么做、没举过完整例子）是它的正当场景。

## 常见失误

- 跳过使用者确认，"方案挺合理的就往下做了"：S7 才发现做的不是他要的。
- 任务按讲课章节切：章节是作者的讲述顺序，不是使用者的任务边界。
- match 只写 skills 不写 topics：同一主张被打了不同标签时归不进去，无处归一大堆。
- 把 confirmed_at 当形式填上：它是 status 判"S4 完成"的依据，也是验收报告里"使用者何时确认了什么"的证据。
