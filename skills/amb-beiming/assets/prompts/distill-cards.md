# 案例卡：任务「${task}」（领域：${domain}）

工程目录：`${project}`。相对路径都相对它。

## 读

1. `${hit_units}`：案例对照表命中的单元（每条含 unit_id、type、title、summary、text 全文、modules 列表——每项 module 所属模块 + why 为什么解释这条判断；一个单元对多个模块时列表有多项，卡里全部写上）。
2. `${pack_dir}/methods.md`：模块 M01… 的主张，写卡时要对得上。
3. `${skill_dir}/references/05-distill.md` 规则节（证层与案例库的边界：案例只用来选法和解释，不进使用者的稿）。卡的格式以本提示词下面的模板为准。

## 写 `${cards_out}`

每个命中单元一张卡，按模块号排序；一张卡不超过约 150 字（不含全文引用），超了就是在复述全文：

```
# ${domain} 案例卡

### u.._.._..　<标题>
- 类型：case | work　说话人：<谁>·<角色>
- 解释哪条判断：M?? <模块名>（对多个模块的用分号并列，各写一句为什么）
- 情境：<使用者会在什么情形遇到类似问题，一两句>
- 作者怎么判：<从这个案例里能看出作者用了哪条判断、哪几步>（用作者原话时逐字加引号并标 unit_id）
- 结果：<案例里发生了什么；语料没说结果就写"语料未提结果">
- 用它时注意：<这个案例的哪些具体事实（人名、数字、行业）不能搬进使用者的稿>
```

## 硬要求

- 卡里的"作者怎么判"是解释，不是复述全文；全文由知识库的案例库保存，卡不抄全文。
- 卡里出现引号的句子必须是单元 text 的逐字子串，且引号后括号里标 unit_id（如「……」（u01_003_02））；`check-layers` 会按 unit_id 核逐字，不符的卡要改。
- 卡的具体事实只用来说明判断，写清"不能搬进使用者的稿"。技能引用卡时按 unit_id 点名，不会把卡里的事实当使用者的事实。
- type=work（作者自己的稿）的卡，多写一项"句式与结构"：这篇稿的段落骨架与可复用句型（逐字摘 1–3 句）。
- 不写过程用语。

## 写 `${report_out}`

卡数；对照表里 module 为 `—` 的单元怎么处理了（没写卡的列 unit_id）；哪些卡的"结果"缺失。
