# 能力方案：按数据分布与使用者的任务清单，定这套工具箱有哪几个任务技能

工程目录：`${project}`。相对路径都相对它。

## 读

1. `${data_table_path}`：原子的真实分布（skills 标签、topics、type、role、confidence、来源组、标签画像、交叉表）。
2. `${precheck_path}`：预检报告，里面有使用者说的"我平时要做的事"清单与语料能支撑什么的初判。
3. `${draft_path}`：候选任务草案（S1 时按语料目录粗列的，可能不准）。
4. `${skill_dir}/references/04-plan.md`：规则节是拆合原则与命名原则，模板节是 tasks.json 的 schema。

## 做

把 skills 标签重新装配成任务技能。每个任务技能必须能回答：

- 输入什么（使用者带着什么来）
- 判断什么（作者的哪套判断决定走哪条路）
- 交付什么（使用者拿走的成品是什么，不是建议）

拆合规则：
- 一个任务的原子里 method+tool 少于 30 条、或 high 少于 20 条，并到最近的邻居，理由写出来。
- 两个标签共享超过一半的 topics，考虑合并成一个任务、用分支区分。
- 使用者清单里有、语料里没有支撑的任务：列进"语料不支撑"，写清缺什么料。
- 语料里有、使用者清单没有的：列进"可选"，说明它服务哪个高频任务。
- 任务数不预设；由使用者高频任务 × 数据支撑决定。
- 作品层（role=作品）原子为主的候选任务：支撑看 method+tool 数，不看 high 数（作品层自述不自动 high），依据里写明这一点。
- 命名用任务说话：任务名写使用者要做的事（"选品判断""开头改写"），不用抽取标签名、层名、"A 类方法论"这类内部分类词。

## 写 `${plan_out}`（给使用者看）

用第二人称对使用者写，让不懂术语的人能确认。不出现字段名、脚本名、段号、schema。结构：

1. 一段话：这批料最擅长解决的三件事。
2. 任务表：| 名称 | 你带什么来 | 作者的哪套判断 | 你拿什么走 | 语料里讲了多少（条 / 其中作者亲历）| 完整案例数 | 对应你清单里的第几项 |
3. 每个任务一小节：来自哪些课 / 哪些文；和相邻任务的分界（什么问题归它、什么问题不归它）；两句能代表它的作者原话（逐字，句子后括号里写原子 id，如「……」（c01_003_012）——使用者不用看 id，但 repool 会按 id 核逐字，不逐字的方案不能分池）。
4. 语料不支撑的任务：缺什么料，补了才能做。
5. 可选任务：为什么值得做。
6. 需要你决定的事（逐条，给默认选项）：工具箱叫什么、每个任务叫什么、要不要并掉哪个。

## 另写 `work/docs/tasks草案.json`（给执行 agent 看，不给使用者）

按 `${skill_dir}/references/04-plan.md` 模板节的 schema 写完整草案：`prefix`（ASCII 短前缀）、每个任务的 `id`（ASCII 短名，将成为技能目录名）、`name`（与方案里的名称一致）、`domain`、`input / judge / deliver`、`match`、`user_job`；`confirmed_at` 留空。使用者确认（或改名、合并）后，执行 agent 据此改成 `work/tasks.json` 并填 `confirmed_at`，再重建任务池。
