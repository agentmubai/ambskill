# 聚类型：形态「${form}」

工程目录：`${project}`。相对路径都相对它。你只读、只写这里指定的文件。

## 料

形态 ${form}，本次 ${n} 篇（该形态共 ${n_all} 篇），来源人：${authors}。每篇一个原件文件，文件头是 id / author / form / file / title，正文是逐字原文。

${listing}

先读 `${brief_path}`（每篇开头 / 结尾各 120 字，逐字）形成类型假设；然后**每篇都要从头读到尾**确认归属——速览只够看开头收尾，中间怎么推进要读全文。读完一篇记一行「这篇怎么开头、中间怎么转、怎么收、归哪个假设」，再读下一篇；不要先读完全部再凭记忆写。篇数多时分批读，每批读完就把归属记进草稿，最后合并。

## 做什么

按**结构**聚类型，不按话题聚：同样讲减脂，一篇是「反常识开头 → 举例 → 一句收」，另一篇是「先给结果 → 拆步骤 → 号召」，这是两类。3–8 类；聚不出稳定的类型就少写，不凑。这个形态常见的起手骨架：${skeleton_hint}——只是给你参照，料里没有的段不要造出来。

一个类型要能回答三问：这类的开头长什么样 / 中间怎么推进 / 怎么收。答不出的不是类型，是话题。

参考线：一个类型 ≥ ${threshold} 篇才够出技能。少于这个数的类型照样列出来，标「薄」，由使用者决定并入、砍掉，还是只当表达样品。

另有一种情形叫**范文型**：某一篇写得特别好、结构独一，值得单独做成「照着这一篇写」的技能。你觉得有这样的篇就单列出来标「可做范文型」，写清为什么；要不要做由使用者定，不是你定。

一篇只归一个类型。实在不像任何一类的，列进「未归类」并写清为什么（残篇、重复、不是本人的、结构独一无二）。不许悄悄漏掉任何一篇。

## 写 `${card_out}`（给使用者看）

用第二人称对使用者写，不用术语、不写文件名、不写编号。结构：

1. 一段话：这批 ${form} 里最常见的几种写法是什么。
2. 每个类型一小节：类型名（使用者一看就懂的叫法）；这类怎么开头、怎么推进、怎么收（各一两句）；两句能代表它的原话（逐字，句子后括号里写原件编号，如「……」（o01_003）——使用者不用看编号，但脚本会按编号核逐字）；大约多少篇。薄的标出来。
3. 未归类的篇：为什么。
4. 需要你决定的事（逐条，给默认选项）：每个类型叫什么、薄的要不要并、要不要砍。

## 另写 `${draft_out}`（给执行者看，不给使用者）

```json
{"form": "${form}", "confirmed_at": "", "user_note": "",
 "types": [{"id": "ascii-short-name", "name": "中文类型名", "brief": "一句话：这类怎么写", "members": ["o01_001", "o01_004"], "thin_ok": false, "exemplar": false}],
 "unassigned": {"o01_009": "为什么不归任何类型"}}
```

- `id` 小写字母开头、只含字母数字 `_` `-`，将成为技能目录名的一部分。
- `members` 里的编号必须是上面列出的原件；一篇只出现一次；每篇要么在某类型里，要么在 `unassigned` 里。
- 你建议做范文型的篇，单独成一个类型、`members` 只放它、`exemplar: true`；使用者不要就会被并掉或删掉。
- `confirmed_at` 与 `user_note` 留空：使用者确认后由执行者填。

## 写 `${report_out}`

每类篇数；你拿不准归属的篇（编号 + 两个候选类型）；结构上像但话题差得远、你合并了的例子；未归类的理由汇总。

## 硬要求

- 类型卡里的每条「原话」必须逐字取自原件正文，不许改写、不许拼接、不许顺一下；后面有脚本核。
- 不评价写得好坏，不加建议，不用行业套话（「要垂直」「要有钩子」）替代对结构的描述。
- 不写过程用语（本轮、子代理）。
- 写完只回复一句：三个文件的路径与类型数。你的回复不算产物，文件才算。
