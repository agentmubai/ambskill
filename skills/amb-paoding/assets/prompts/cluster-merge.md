# 合并类型草案：形态「${form}」（${parts} 块 → 一份）

工程目录：`${project}`。相对路径都相对它。你只读、只写这里指定的文件。

## 读

1. 全部分块草案与分块类型卡（每块由不同的人读了 ${n_all} 篇里的一部分，各自按结构聚了假设）：
${part_drafts}
2. `${brief_path}`：全部 ${n_all} 篇的开头 / 结尾各 120 字，逐字。
3. 拿不准某篇归属时，读它的原件全文（路径在分块草案的 members 对应 `work/kb/originals/<编号>.md`）。

## 做什么

把 ${parts} 份分块草案合成一份。分块各自取的名字不同，但描述的结构可能是同一个：**按结构合并**——「反问起 → 三分法 → 回到反问」和「一个问题起头分三种人最后反问」是一类。

- 合并后 3–8 类；每类 ≥ ${threshold} 篇才够出技能，少的标薄，不砍——由使用者定。
- 一篇只归一个类型。分块之间同一篇不会重复（每块只归自己的篇），但合并后要核：每篇恰好出现一次，要么在某类里，要么在 unassigned 里。
- 分块里「未归类」的篇，合并时看能不能进别人块里聚出来的类型；进不了就留在 unassigned 并保留理由。
- 类型名这时候取：使用者一看就懂的叫法；`id` 用 ASCII 短名。
- 每类挑两句能代表它的原话（逐字，句后括号编号），可以从分块类型卡里取，取的时候回原件核一眼是不是逐字。

## 写 `${card_out}`（给使用者看）

用第二人称对使用者写，不用术语、不写文件名、不写编号。结构：

1. 一段话：这批 ${form} 里最常见的几种写法是什么。
2. 每个类型一小节：类型名；这类怎么开头、怎么推进、怎么收（各一两句）；两句能代表它的原话（逐字，句子后括号里写原件编号，如「……」（o01_003）——使用者不用看编号，但脚本会按编号核逐字）；大约多少篇。薄的标出来。可做范文型的单篇单列并说明。
3. 未归类的篇：多少篇、为什么。
4. 需要你决定的事（逐条，给默认选项）：每个类型叫什么、薄的要不要并、要不要砍、范文型要不要做。

## 写 `${draft_out}`（给执行者看）

```json
{"form": "${form}", "confirmed_at": "", "user_note": "",
 "types": [{"id": "ascii-short-name", "name": "中文类型名", "brief": "一句话：这类怎么写", "members": ["o01_001", "o01_004"], "thin_ok": false, "exemplar": false}],
 "unassigned": {"o01_009": "为什么不归任何类型"}}
```

- `members` 编号必须是原件库里的；每篇恰好出现一次（某类里或 unassigned 里）。合并完自己数一遍：types 里所有 members 数 + unassigned 数 = ${n_all}。
- `confirmed_at` 与 `user_note` 留空。

## 写 `${report_out}`

分块之间怎么对应合并的（哪几块的哪几个假设并成了哪个类型）；有分歧的篇（分块归 A、你改成 B 的）及理由；每类篇数；未归类汇总。

## 硬要求

- 类型卡里每条「原话」逐字取自原件正文，不改写、不拼接；脚本核。「」只包原话，编号紧跟。
- 不评价好坏，不加建议，不用行业套话替代结构描述。
- 写完只回复一句：三个文件路径、类型数、篇数核对结果。
