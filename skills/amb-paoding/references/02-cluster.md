# 02 P3 聚类型

## 目标与产出

同一形态内按结构聚出 3–8 个类型，写成使用者看得懂的类型卡；使用者定类型名与取舍。这是唯一参与点。

产出：`work/docs/类型卡-<形态>.md`、`work/types/<形态>.draft.json`（子代理）；`work/types/<形态>.json`（你，使用者确认后填 confirmed_at）；confirm 记录。完成 = confirm 记录 ok。

## 动作

1. `paoding.py cluster <形态>`：生成提示词（预检报告没有结论会被拒）。派一个子代理；它读该形态全部原件，写类型卡与草案。
2. 你先审草案：类型是不是按结构分的（不是按话题）；每类能不能答"开头长什么样 / 中间怎么推进 / 怎么收"；薄的有没有标；未归类的有没有理由。
3. 交使用者看类型卡。他会改名字、合并、砍掉、或说"薄的那个我也要"。**没有这一步不许进 P4。**
4. 按他的话把草案改成 `work/types/<形态>.json`：改名、合并成员、砍类型都在这里落地；薄的他要就标 `thin_ok: true`；填 `confirmed_at` 与 `user_note`（他的原话）。
5. `paoding.py confirm <形态>`：查 confirmed_at、id 合规、成员归属、无漏篇。不过就改到过。
6. 多个形态各走一遍；不想做的形态在预检报告里写"收缩"即可。

## 规则

- 按结构聚，不按话题：开头怎么起、中间怎么转、怎么收。同一话题两种结构是两类；两个话题一种结构是一类。
- 一个类型要能答三问（开头 / 推进 / 收束）；答不出的是话题，不是类型。
- 一篇只归一个类型。每篇要么在某类型里，要么在 unassigned 里带理由——不许悄悄漏。
- 类型卡里给使用者看的原话必须逐字并带编号（他不用看编号，脚本会核）。
- 类型 id 是 ASCII 短名，会成为技能目录名；中文名用 name。
- 薄类型（< 参考线）只提醒不拦：出不出由使用者定，记在 thin_ok。
- 范文型：某一篇写得特别好、结构独一，使用者点名单独做 → 单独成一个类型、members 只放它、`exemplar: true`，user_note 记他的原话。子代理可以在类型卡里建议「可做范文型」，做不做由使用者定。不许用 exemplar 绕过薄类型提醒（confirm 查 user_note）。
- 增量（`cluster <形态> --update`）只给新篇分类，不重聚旧的；新类型出现要再过使用者。新形态的料不走 --update，按增量报告的档走（见 06）。同形态但来源人是新的，让子代理先判像不像，像才并入。

## 依据

外层：任务分析——技能的单位是"使用者要写哪一类"，按他要产出的东西拆，不按对方讲了什么话题拆。

内层（可观察）：
1. `types/<形态>.json` 含 confirmed_at，每类 id / name / brief / members 非空。
2. confirm 无漏篇、无重复归属、无跨形态成员。
3. 类型卡里的原话经 confirm 逐字核通过（能力方案写法的直接延续）。

为什么这样定：
- 使用者必须确认：类型体系是他用的；执行者按料切出的类型再合理，也可能是他从不写的东西。
- 一篇一类：技能之间边界靡清，路由器判不了；覆盖表也算不清。
- 薄类型不硬拦：有的人只有 8 条同结构的朋友圈，也值得一个薄技能——但要他知道薄。

## 常见失误

- 子代理按话题聚（"减脂类 / 育儿类"）：退回重聚，提示词里已写明按结构。
- 类型太多（十几个）：每类几篇，全是薄的。让子代理合并结构相近的。
- 跳过使用者确认，"草案挺合理就往下做了"：验收时才发现做的不是他要的。
- 把 confirmed_at 当形式填上：它是 status 判 P3 完成的依据，也是验收说明里"使用者何时确认了什么"的证据。
- 忘了 unassigned：漏掉的篇在覆盖表里永远看不到。
