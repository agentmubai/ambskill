# 06 交付与 P6 增量

## 目标与产出

交付：把草稿技能装配成自包含成品，附原件库与拆解层，写给接收方的 README。增量：新篇只入原件库，只重拆受影响的类型，旧的不动。

产出：`product/<箱名>/`（或 `--dest`）；deliver 记录。增量后各门槛记录重新 ok。

## 动作

交付：
1. `paoding.py deliver <箱名> [--dest 目录] [--no-kb]`：门槛是 lint ok 且未过期；轻验收没有只提醒。脚本复制 skills/、放 fact_check.py、附 kb/（原件库 + 写法书与覆盖表）、写 README、跑成品体检。
2. 体检 FAIL 就改草稿重新 deliver。
3. 把成品目录交给接收方；说清 `skills/` 下每个目录拷进宿主技能目录即可，`kb/` 与根 `scripts/` 不是运行依赖。

增量：
1. 新篇放进原作品目录 → `paoding.py survey --update`（只追加，旧编号不变）。脚本出 `work/docs/增量报告.md`，把新料分三档，**先看这份报告再动**：
   - ① 形态已有、类型已确认 → 正常增量。来源人是新的会另提醒：让聚类型的子代理先判像不像，像才并入。
   - ② 新形态、篇数 ≥ 参考线 → **不是同一批次**。不并进旧类型；当新形态走一遍 P3–P5，在同一个箱子里出新技能（路由器先判形态），最后 `compose --router` 重写路由器。
   - ③ 新形态、篇数不够 → **不是同一批次也不够**。只 `ingest` 存原件，标待补料，不出技能、不动旧的；补够再来，或使用者点名一篇做范文型。
2. `paoding.py ingest`（只写新原件）。
3. ①档形态：`paoding.py cluster <形态> --update` → 派子代理只给新篇分类 → 改 `types/<形态>.json`（新类型要再过使用者；只是加成员不用）→ `confirm <形态>`。②档形态：`cluster <形态>`（不带 --update）走完整 P3。
4. 受影响的类型：`paoding.py pattern <形态-类型> --update` → 派 → `check`；零引用篇 dispose。
5. `paoding.py compose <形态-类型> --sync-refs` → `lint`。新类型走完整 compose；有新形态就 `compose --router` 重写路由器。
6. 轻验收可选；`deliver` 重新装配。

## 规则

- `--dest` 只允许覆盖空目录或上一次交付的成品（同时有 README.md 与 skills/）；别的一律拒绝。这是全链路唯一一处会删目录的代码，不替使用者删来历不明的东西。
- 成品默认附 kb/：原件库是接收方溯源与下一轮增量的输入；技能运行不读它。`--no-kb` 时 README 写明增量需回生产工程。
- 成品 README 写给接收方，用"你"；写明来源人几位、"类型不是某人"、事实不搬、只用有权使用的内容。不出现工程路径与过程用语。
- 增量只动受影响的：新篇没落到的类型，写法书与技能一字不改；改了的门槛记录会自动 stale，按 status 补跑。
- 新类型必须再过使用者；给旧类型加成员不必。
- 不同形态的料永远不并进同一个类型：销售信的箱子加进短视频，短视频自己聚类型、自己出技能，和销售信在同一个箱子里由路由器分流。脚本层面 cluster 本来就按形态跑，增量报告只是把这件事说出来，免得执行者顺手当"补料"处理。
- 一篇写得特别好、想单独做：走范文型（exemplar），不是增量。

## 依据

外层：自包含交付——接收方不需要本技能、不需要生产工程也能用；增量按依赖哈希只重做变了的部分。

内层（可观察）：
1. 成品体检（`lint --product`）全 PASS：README 在、根 fact_check 在、无 work/ 路径与绝对路径。
2. deliver 记录的 dest 是相对工程根的路径，工程搬家后 status 仍能找到成品。

为什么这样定：
- 安全覆盖：同仓 amb-beiming 深审时发现过 `--dest` 直接 rmtree 使用者目录的问题，这里从第一版就按修后的规则写。
- 附原件库：三层设计的第一层不能在交付时丢掉，否则接收方拿到的又是"拆解压进提示词"。

## 常见失误

- 把 `--dest .` 指向当前目录：会被拒（目录非空且不像成品）；换空目录。
- 增量后直接 deliver：lint 记录已 stale，deliver 会拒；先 sync-refs → lint。
- 新类型没过使用者就 compose：confirm 会因 confirmed_at 过期而拒，不要手改时间蒙混。
- 成品 README 手改来源人为某个人名：成品写的是类型，来源人只在"拆了谁的作品"一句里出现。
